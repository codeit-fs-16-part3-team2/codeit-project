# 최애의 포토 구현 이슈 목록

구현·검증 추적 · 2026-11-26 · [프로젝트 계획](plan.md) / [API 계약](api.md) / [DB 설계](DB.md) / [결정 기록](ADR.md)

## 범위·착수 기준

프로젝트 기간은 2026년 11월 25일(수)부터 12월 15일(화)까지다. 12월 4일에 핵심 거래를 먼저 배포 검증하고, 12월 15일에 최종 필수 기능을 인수한다. P2는 필수 범위 검증 뒤 일정에 여유가 있을 때 진행한다. 데이터 작업은 [ERD](ERD.md)와 [Prisma 스키마](../api/prisma/schema.prisma)를 함께 참고한다.

프론트엔드는 [API 계약의 응답 형식](api.md#응답-필드)에 맞춘 mock으로 바로 시작한다. 다른 화면이 준비되면 이동 흐름을 연결하고, 미정인 입력 정책은 확정 후 검증에 반영한다. 실제 API 연결과 배포 검증에는 실제 응답과 DB 반영 결과를 사용한다. 상태는 검증 결과가 기록되면 갱신한다.

<a id="issue-iss-be-01"></a>
### ISS-BE-01 · [BE] Express·PostgreSQL 기반과 시드 준비

- **목표** 12월 4일 배포
- **우선순위** P0
- **착수 선행** [ISS-COMMON-01](#issue-iss-common-01)
- **관련 모델** `User`, `PhotoCard`, `Inventory`

**완료·검증 기준**

- [ ] Express 5에서 라우터·컨트롤러·서비스·저장소의 책임을 나누고 공통 성공·실패 응답을 적용한다.
- [ ] Prisma 7 검증과 빈 개발 DB 마이그레이션을 통과한다. 수량·잔액·가격 범위 제약을 확인하고 구매 수량 0과 음수 잔액은 저장할 수 없음을 검증한다.
- [ ] 시드 판매자가 판매 가능한 같은 카드 세 장 이상을 보유한다. 시드를 반복 실행해도 카드와 보유 수량이 중복되지 않는다. 시드 작성 때 장르 허용 목록을 확정하고 등급·장르가 API 계약과 일치하는지 확인한다.
- [ ] 시드 카드의 최소 가격을 지정하고, 카드별 전체 보유 수량이 `issuedQuantity`와 일치하는지 확인한다.
- [ ] Render의 Express API가 PostgreSQL에 연결된다.

**시드와 시연 데이터**

[ERD 초안](ERD.md)의 `User`, `PhotoCard`, `Inventory` 구조에 맞춰 시드 데이터를 새로 작성한다. 카드별로 판매자의 초기 보유 수량과 발행량을 맞추고, `Inventory.lastAcquiredAt`에는 시드 지급 시각을 기록한다. 12월 4일에는 판매자 한 명과 같은 종류의 카드 세 장 이상으로 구매 흐름을 먼저 확인한다. 최종 제출의 교환 시연에는 종류가 다른 카드를 추가로 준비한다. 실제 카드·이미지·장르 목록은 시드 작업에서 확정한다.

| 구분 | 준비할 데이터 | 확인 기준 |
| --- | --- | --- |
| 시드 | 판매자 계정과 판매 가능한 같은 종류의 카드 세 장 이상 | 판매자가 로그인 후 마이 갤러리에서 카드를 확인한다. 카드 이름·등급·장르·설명·이미지와 초기 발행량을 시드에 넣고, 시드에서 사용한 장르 목록을 API와 화면 필터에 공유한다. |
| 판매 등록 | 시드 판매자가 시연 중 해당 카드 세 장을 장당 4P에 등록 | 판매 상세에 장당 4P와 잔여 세 장이 표시된다. |
| 구매 | 시연 중 다른 브라우저 세션에서 신규 회원을 가입시키고 카드 두 장을 구매 | 가입 직후 10P에서 8P가 차감되고, 구매자 갤러리에는 두 장이 표시된다. 판매자 잔액은 8P 증가하고 판매글에는 한 장이 남는다. |

시연을 반복하기 전에는 판매자에게 해당 카드 세 장을 다시 등록할 수 있는지 확인하고, 구매자는 사용하지 않은 이메일과 닉네임으로 가입한다. [예시 요청](api.http)의 01~11 순서를 따른다.
